# Engineering Digest — 2026-11-21

Seven reads on failovers that route writes to the wrong place, scaling that hits the database wall, cloud bills cut with real numbers, and why RAG demos work while production systems quietly fail. The theme of the day: **failover traps, scaling walls, honest RAG**.

## Distributed Systems

### 1. New connections failed, old ones worked: the failover that sent writes to a read-only database — Kashif Manzer
http://dev.to/kashif_manzer/new-connections-failed-old-ones-worked-the-failover-that-sent-writes-to-a-read-only-database-m5b

On October 28 the RIPE Database started refusing some updates while others sailed through: a failover to the standby load balancer silently sent new connections to the read-only database while old connections kept writing to the primary. The fix isn't more failover testing — it's testing failover with a real write, not a ping. A short, sharp lesson in why health checks that only read will never catch a write-path misconfiguration.

### 2. Our RabbitMQ Queue Had Zero Errors. We Were Still Losing Customer Transactions — Devrim
https://medium.com/engineering-playbook/our-rabbitmq-queue-had-zero-errors-we-were-still-losing-customer-transactions-edd76a554d85

RabbitMQ showed zero errors, healthy nodes, and a normal processing rate — while customer transactions quietly vanished from the accounting records. The gap was between the broker accepting a message, the consumer receiving it, and the business transaction actually committing. The piece walks through quorum queues, publisher confirms, and ack timing to show why 'delivered' and 'done' are different guarantees, and what to wire together so a crash can't eat a payment.

## Java/Spring Boot

### 3. We Scaled Our Java System 4×. Throughput Barely Moved. Then the Database Started Failing — Devrim
https://medium.com/engineering-playbook/we-scaled-our-java-system-4-throughput-barely-moved-then-the-database-started-failing-1998e2e76ee1

Traffic rose from 1,200 to 2,100 requests per second, the team quadrupled replicas from 12 to 24 — and p99 latency went from 420ms to 4,800ms while the backlog barely moved. The bottleneck was never CPU: every replica multiplied HikariCP connections against the same PostgreSQL, and the queueing math made more capacity strictly worse. A case study in why scaling the stateless tier first is the wrong instinct when the database is the constraint.

### 4. Spring Boot Production Failures: 12 Problems That Pass Tests and Break Real Systems — The Systems & Architecture — Javarevisited
https://medium.com/javarevisited/spring-boot-production-failures-12-problems-that-pass-tests-and-break-real-systems-257c1c7b6cd9

Twelve failure modes that all pass the test suite: HikariCP exhaustion, @Transactional holding connections through network calls, Hibernate N+1, PostgreSQL lock contention, and a failover that leaves Spring Boot unreachable. Each one comes with the symptom you'd actually see on call and the diagnostic step that narrows it down. Keep it next to the runbook — it's the debugging order that matters more than any single fix.

## Cloud Infrastructure

### 5. How I cut our cloud bill by 82% in four weeks, and what it cost us — scnozdemir
https://medium.com/@scnozdemir/how-i-cut-our-cloud-bill-by-82-in-four-weeks-and-what-it-cost-us-9c4a22e1ea2d

A real bill, cut from $1,472 a month to $267 in four weeks across 75 pull requests: CI runners moved to a pool that scales to zero, requests sized from measured peaks instead of guesses, and nodes switched off one by one as reserved memory was freed. The honest part is the trade-off list — single-node production, a halved database, no staging — which is exactly what makes the numbers believable. For anyone who has ever been told their Kubernetes cluster 'needs' three environments.

### 6. Cost-aware architecture: tearing down a cloud bill — Jitin Bahri
https://medium.com/@jitinbahri/cost-aware-architecture-tearing-down-a-cloud-bill-2196b772fb24

A methodical teardown of where cloud money actually leaks — idle resources, over-provisioning, data transfer, storage that never expires — with the attribution work first: tag everything, export the billing data, allocate shared Kubernetes costs with OpenCost or Kubecost. The durable point is that cost is an architecture property, not a quarterly cleanup project, and the habits that keep leaks fixed are the same ones that keep latency and reliability honest.

## Applied AI/RAG

### 7. Why RAG Fails in Production (2026): 7 Failure Points and Real Fixes — Ajay Kumar
https://www.ajayk.sh/blog/why-rag-fails-in-production-2026/

Every RAG demo works; most production systems quietly don't. The piece maps seven failure points — chunking, retrieval misses, stale indexes, permission leaks, the evaluation gap — and backs each fix with a number, like hybrid search plus reranking cutting retrieval misses from 5.7% to 1.9% of queries. The sharpest finding: quality drops off a cliff past roughly 2,500 tokens of context, so chunking is a measurement problem, not a config default. For teams whose RAG system is live and whose answers are slowly getting worse.
