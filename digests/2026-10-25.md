# Engineering Digest — 2026-10-25

Seven reads on production judgment: the fix that looks right, the number that lies, and the evidence buried at position eight. The theme of the day: **when the obvious fix is wrong**.

## Distributed Systems

### 1. Production Recovered in Six Minutes. Our Bus Factor Fell to One. — Yusuf Seyitoglu
https://medium.com/@yusufseyitogluu/production-recovered-in-six-minutes-our-bus-factor-fell-to-one-be4495393e7f

A single Consul command drained a lagging payment queue, but only because one engineer checked five things first: message age vs. depth, latency vs. concurrency, idempotency, autoscaling, and triggers. The postmortem recorded the command and missed the reasoning, so the next engineer copied the fix into a CPU-bound incident where it made things worse. For anyone writing runbooks: document the diagnosis, not just the command.

## Java / Spring Boot

### 2. The 3-Line Config Change That Took Down Production: A Spring Boot & HikariCP Outage Post-Mortem — Sopheaktra Yorn
https://medium.com/@yornsopheaktra/the-3-line-config-change-that-took-down-production-a-spring-boot-hikaricp-outage-post-mortem-703c557991df

A routine pull request meant to optimize database concurrency pushed P99 latency from 35ms to 30 seconds while CPU, heap, and database all looked healthy. The system was not starved of resources; it was standing still. A sharp reminder that pool settings are load-bearing configuration, and that healthy infrastructure metrics can hide a concurrency deadlock.

### 3. Spring Boot 4 + Java 25: 12 Things You Should Stop Doing in Your Spring Data JPA Code — Navya Devadiga
https://medium.com/system-design-architecture-deep-dives/spring-boot-4-java-25-12-things-you-should-stop-doing-in-your-spring-data-jpa-code-bb8d4291a3c1

Twelve JPA habits measured on Spring Boot 4.1 and Hibernate 7.4, each with the statement count it actually cost: findAll() plus an in-memory filter sent 1,001 statements to return 200 rows, and an EAGER @ManyToOne turned one query into eleven. The numbers make the case better than any style guide could: check what your repository methods really send before blaming the database.

## Cloud Infrastructure

### 4. How We Cut AI Infrastructure Costs by 40% Through Kubernetes GPU Optimization — Ujjwal Trivedi
https://medium.com/@ujjwalt429/how-we-cut-ai-infrastructure-costs-by-40-through-kubernetes-gpu-optimization-7f27c522b142

GPU utilization sat at 25 to 30 percent because every inference pod requested a full GPU, and nodes stayed up overnight simply because nothing told the cluster it could shrink. Measuring with DCGM and Prometheus turned a vague bill complaint into a concrete fix. For teams running AI workloads on Kubernetes: measure utilization first, then right-size, not the other way around.

### 5. Overinflated Kubernetes Resource Requests: Cost and Fixes — PerfectScale
https://www.perfectscale.io/blog/overinflated-kubernetes-requests

Kubernetes bills follow requests, not usage, and JVM startup peaks are a classic reason requests stay inflated for a pod's whole life. The fix is to size startup and steady state separately, using startup probes to protect the slow start instead of paying for peak CPU forever. Especially relevant if your Spring Boot services carry generous CPU requests from their first deploy.

## Applied AI / RAG

### 6. Reranking in Production RAG: Cross-Encoders, LLMs & MMR — Rajkumaar
https://medium.com/@er.rajkumaar/reranking-in-production-rag-how-to-get-the-most-relevant-context-to-your-llm-6ea84a9ecbe7

Retrieval found the exact approval matrix for a 12-million-euro credit decision, but buried it at position eight behind broader policy documents. Reranking with cross-encoders, LLM rerankers, or MMR is what puts the decisive evidence where the model will actually use it. A practical walkthrough of the accuracy, latency, and cost trade-offs of each approach, with code.

## Applied AI

### 7. Black October Agent Postmortems: The One Fix — Max Quimby, AgentConn
https://medium.com/@computeleap/black-october-agent-postmortems-the-one-fix-agentconn-blog-1e514e23a006

Four real production agent failures from October 2026, all tracing to the same root cause: agents running with ambient human credentials or unscopable machine access. The fix is not a new product but a configuration change: scoped, per-agent identity with least-privilege boundaries. If you are shipping agents to production, this is the cheapest hardening you can do this week.
